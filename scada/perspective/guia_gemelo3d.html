⚡ ¿Cómo funcionan las Named Queries en Ignition Perspective 8.3?

En Ignition 8.3 ya no existen archivos binarios ocultos para las consultas SQL: cada Named Query es una carpeta en ignition/named-query/CMAPSS/<Nombre>/ compuesta por solo 2 archivos de texto plano:

1. query.sql --> La consulta SQL con parámetros (:assetId, :simCycle) 2. resource.json --> Define la BD ("twin") y el tipo de cada parámetro: "parameters": [ { "identifier": "assetId", "sqlType": 7 }, // 7 = String { "identifier": "simCycle", "sqlType": 2 } // 2 = Integer ]

⚠️ Las 2 Reglas de Oro para evitar Puntos Rojos en Named Queries

1. Error clásico: Pasar un número literal en el JSON del binding (ej. "startCycle": 1). Perspective exige que todos los parámetros en view.json sean Strings ("startCycle": "1" o "{view.custom.simCycle}").
2. Formato JSON: Al usar "returnFormat": "json" en el binding hacia view.custom.kpis, Ignition devuelve un arreglo de diccionarios accesible directamente como {view.custom.kpis[0].rul_cycles}.

🔗 El Patrón Moderno: Centralizar en view.custom (Adiós a ../../..)

Cuando anidas tarjetas dentro de contenedores Flex en Perspective, las rutas relativas (../Sibling o ..../KPI_Row) se rompen en cuanto agregas un contenedor nuevo. La arquitectura recomendada es:

// En la raíz de view.json: "custom": { "selectedAsset": "cmapss_1", "simCycle": 192 }, "propConfig": { "custom.kpis": { "binding": { "type": "query", "config": { "queryPath": "CMAPSS/turbofan_kpis", "returnFormat": "json", "parameters": { "assetId": "{view.custom.selectedAsset}", "simCycle": "{view.custom.simCycle}" } } } } }

El Dropdown y el Slider se enlazan con "bidirectional": true a view.custom.selectedAsset y view.custom.simCycle. Así, cualquier componente en cualquier nivel lee {view.custom.kpis[0].lpt_temp_s4} con 0 errores.

🎨 ¿Cómo hicimos el SVG Animado (2D) y el Gemelo 3D WebGL sin recargar?

1. SVG Dinámico en ia.display.image: Enlazamos props.source a una expresión concat("data:image/svg+xml;utf8,<svg...>", ...). Usamos rgb(...) y %23 en vez de # para que el navegador no corte el URI en los colores hexadecimales.

// 2. Sincronización 60 FPS con el Visor 3D (ia.display.iframe): // En lugar de usar '?query=' (que recarga el iframe y reinicia la cámara 3D), // pasamos los sensores en el FRAGMENTO HASH (#): concat("http://localhost:8095/turbine3d.html#asset=", {view.custom.selectedAsset}, "&cycle=", {view.custom.kpis[0].current_cycle}, "&s11=", numberFormat({view.custom.kpis[0].hpc_static_press_s11}, "0.00"))

Dentro del visor 3D, window.addEventListener('hashchange', ...) recibe los datos al instante sin parpadear ni perder el ángulo de rotación del mouse.

🤖 ¿Qué hace el Servidor MCP (src/mcp_server.py)?

El Model Context Protocol (MCP) conecta al agente de IA directamente con el modelo XGBoost + MAPIE y con el contenedor Docker twin-ignition mediante 6 herramientas:

• get_fleet_status() --> Clasifica las 100 turbinas (CRITICAL/WARNING/HEALTHY) • predict_engine_rul(id) --> Predice RUL y extrae los 5 sensores clave del motor • get_sensor_telemetry(id) --> Calcula el Z-Score de deriva física contra la base sana • get_model_diagnostics() --> Reporta RMSE (18.29), R² (0.79) y ranking de sensores • audit_perspective_hmi() --> Audita view.json en Docker buscando errores de bindings • deploy_perspective_hmi() --> Genera el JSON ISA-101 y lo inyecta en twin-ignition

Etapa 1: Admisión y Ventilador Frontal (FAN)

El Fan frontal acelera una gran masa de aire frío (dividida entre el ducto de bypass externo y el núcleo del motor). En el dataset C-MAPSS FD001, sus sensores principales son T2 (s1: 518.67 °R) y la velocidad física del ventilador Nf (s8: ~2388.2 rpm).

Sensores en Named Query (turbofan_kpis.sql): • fan_inlet_temp_s1 (Señal s1 - Temperatura Total Entrada Fan [°R]) • fan_speed_s8 (Señal s8 - Velocidad Física del Fan [rpm])
